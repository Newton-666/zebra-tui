# Krystal 设计草案：底层模型与成员规格（Agent Spec）

> 状态：**草案，未实现**。本文只定设计（字段、流程、护栏、契约），不含实现代码。
> 目的：让「不同情况需要不同能力的 agent」变成**可声明、可授予、可强制**的事情，
> 同时保持平台极简——**不预设有哪些 agent，只提供造 agent 的方式**。

## 0. 一句话纲领

> 极简的单位是**概念**，不是行数。
> pi 用少量工具换掉整个 agent 框架；Krystal 用**四个原语**换掉整个多 agent 框架：
> **身份、派工、白板、汇报**。
> 落到数据上就是：**一份极小的成员规格 + 一个生成器 + N 种驱动。**

新增能力的验收标准（两条，任一不满足就是我们在偷偷加第二个框架）：

1. **能否在不碰驾驶舱的前提下加一种成员？** 能 → 我们是 platform。
2. **新能力是否都是四个原语的组合？** 是 → 极简成立。

## 1. 两个模型，互不干预

平台里存在两种**完全独立**的模型职责，用户可以分别设定，彼此零影响：

| | **搭建模型**（Krystal 底层模型） | **成员模型** |
|---|---|---|
| 何时用 | **搭建期**（一次性） | **运行期**（持续） |
| 职责 | 让建队更智能：一句话 → 成员规格、**装备分配**、协作协议 | 那个成员自己的脑子（干活、思考） |
| 谁选 | 用户在平台配置里设定一次 | 用户逐个成员选（同今天的 `:model`） |
| 存放 | 平台配置的 `builder` 段 | `team.json` 的 `members[].model` |
| 影响面 | 只影响「建队质量」 | 只影响该成员的能力与成本 |
| 互相影响 | **零** | **零** |

**统一点（不增加概念）**：搭建模型本身就是一个**驱动槽位**。
生成器只认「给我一个会思考的脑」：

- 首选：平台模型（原生调用，用户自定义端点/密钥/模型名）
- **无静默回退（已定）**：未配置搭建模型时，点「一句话建队」直接引导先去配置（见 §5.1），
  不允许默默借用外部 CLI——把现在静默绑定的行为变成显式配置门槛

## 2. 成员规格 AgentSpec

一句话不生成代码，生成**规格**。字段刻意压到 5 个（+1 待定）：

| 字段 | 说明 | 例 |
|---|---|---|
| `mission` 使命 | 它为什么存在、产出什么 | 只读审查接口设计，输出问题清单 |
| `tools` 工具子集 | **能力在这里才是真的**（不是提示词里的拜托） | `read`, `board`, `report` |
| `scope` 作用域 | 能碰哪里、只读或可写 | 只读 / 仅工作副本内可写 |
| `budget` 预算 | 模型、token/成本上限 | 中继用便宜模型，实现用强模型 |
| `topology` 拓扑 | 能否派工、向谁汇报、平级还是组长 | 可派工给 builder，向人类汇报 |
| `contract` 产出契约（**待定**） | 什么算做完、谁来验收 | 通过测试 / 产出清单 |

### 2.1 能力 = 一个终端 + 权限策略（已定，取代工具子集词表）

每个成员**只有一个工具：终端**（git + gh 覆盖读/写/传 GitHub 全部需求），
能力差异 = 挂在终端上的**策略档位**：

| 档位 | 终端策略 | 适用 |
|---|---|---|
| 阅读者 | 只读白名单：`ls` `cat` `grep` `rg` `find` `git status/log/diff/show` `gh pr view/list`…；工作副本只读挂载 | 审查、调研 |
| 验证者 | 阅读者 + 测试命令白名单（`npm test`…），仍不可写 | 验收 |
| 写作者 | + 写文件、`git add/commit`；push 仅限自己的分支 | 实现 |
| 协调者 | **没有终端**，只有白板/派工/汇报 | 管家 |

**三层强制**（缺一不可，只拦命令不够——`python -c` 就能绕过）：

1. **命令白名单**：未列入 = 拒绝（不是黑名单）
2. **OS 沙箱**：终端跑在工作副本里，按档位只读/可写挂载
3. **凭据与分支保护**：每个 agent 用细粒度 token，只能推 `agent/<名字>/*` 分支；main 开分支保护，合并只走 PR 由人确认

插件成员（外部 CLI）套同一层：OS 沙箱包住整个进程。

> 保真度：原生成员三层都硬；插件成员靠 OS 沙箱这一层硬，其余靠约束。

### 2.2 紧凑语法（示意）

```
MEMBER <名字> <使命> | tools read,board,report | scope 只读 | tier 便宜
```

## 3. 搭建流程（向导改动）

现状：`模式 → 新建团队 → 人数 → 每个成员「名字 + 类型」`

改为：

```
模式 → 新建团队 → 人数 → 每个成员 [ New Krystal Bot | Plugin Agent ]
                            ├─ Krystal Bot
                            │    └─ 「你想让我做什么？」→ 一句话
                            │       → 搭建模型产规格（使命 + 装备）
                            │       → 显示一行规格，可改 → 确认
                            └─ Plugin Agent
                                 └─ 选插件 + 名字（现有流程）
                                    （搭建模型仍可生成职责与装备，用于简报注入）
```

**产品层面的关键收益**：默认路径不再要求用户知道外部 CLI 的名字——插件是进阶选项。

**成员模型**：沿现有方式选择（原生成员与插件成员一样，都可由用户指定模型）。

## 4. 驱动契约 MemberDriver

驾驶舱（网格 / cell / 派工 / 白板）**不得知道**成员背后是哪种驱动。

```
spawn(spec)   -> handle      // 启动
send(handle, text)           // 人类/系统 → 成员（派工、人类指令）
poll(handle)  -> Event[]     // 成员 → 系统（结构化事件，不是屏幕）
screen(handle)-> string[]    // 只给格子显示的行
status(handle)-> {state, note, cost?}
kill(handle)
```

- **原生实现（Krystal Bot）**：一个 loop + 自己渲染行；状态、成本、等待依赖都是真实值
- **插件实现（外部 CLI）**：现有 tmux 那套，**抓屏藏在驱动内部**

这就是「抓屏从引擎必需降级为某个驱动的实现细节」——一整类偶然复杂度被关进笼子。

## 5. 平台配置

```
~/.krystal/config.json          # 全局；团队可覆盖
{
  "builder": { "baseUrl": "https://…/v1", "apiKey": "…", "model": "…" }
}
```

### 5.1 配置入口：第一页菜单项（已定）

向导第一页（选择模式）增加一项：

```
选择模式：
  新建团队
  一句话建队
  历史群聊
  Platform model      ← 新增
  退出
```

进入后的子流程（**用户唯一必填的是 API Key**）：

1. **选择提供商**：预设 baseUrl（DeepSeek / OpenAI / Moonshot / 通义 / 智谱 / OpenRouter / Ollama / LM Studio，
   另有「自定义 Base URL」兑底）——预设是**数据**，不是代码
2. **填 API Key**（唯一必填；本地服务如 Ollama 可留空占位）
3. **动态拉取模型列表**（GET /models）→ 选择；也可手动输入模型 id 兑底
   —— provider 侧上新模型**自动可见**，无需更新 Krystal
4. **测试连接**：发一个几十 token 的最小请求，成功后才允许保存
5. 清除配置 → 回到未配置状态；返回

设计原则：**入口在第一页**（换平台模型是低频但全局的动作，放在最高层级）；
**provider 是预设数据、模型动态拉取**（向 pi 学习：尽可能预设好，用户只填 key 测试）；
不再另设 `:builder` 之类的运行时命令，避免同一件事有两个入口（不加概念）。

- 协议优先 **OpenAI 兼容 chat completions**：一个适配器覆盖绝大多数云端与本地服务（最大化覆盖、最少代码）
- 环境变量优先，配置文件可覆盖
- 未配置时的行为见 §1「回退」：显式借用插件驱动，并在界面上说明

## 6. 护栏（五条）

1. **能力是数据，不是代码**：不允许用户编写自定义工具实现（那就是插件框架 = 第二个框架）
2. **可见可改**：一句话 → 规格先显示成一行，用户确认或修改后才创建（不做黑箱魔法）
3. **不预设 agent**：平台自带零个预设成员，只提供造成员的方式（示例只能是数据/模板）
4. **回退显式**：借用插件驱动生成时必须提示，禁止静默绑定
5. **拒绝越权**：原生成员被要求做规格外的事（如写代码而无 `write`）时应拒绝并派工，**这个拒绝本身就是设计**

## 9. Krystal Bot 的解剖学（它也是一个 agent）

**结论：与 pi 同构——loop + 工具调用 + 流式思考 + 渲染，四件套一件不少。**
差别不是「更少」，而是三件事归平台所有：工具按档位授予、渲染是原生的、上下文是协议原生的。

### 9.1 Loop（与 pi 同构）

```
等事件（人类一句话 / 成员汇报 done·blocked·ask / 白板变更 / 依赖变化）
  → 组上下文（身份 + 档位策略 + 协议 + 滚动窗口）
  → 调模型（SSE 流式）
  → 执行 tool_calls（过策略闸门）→ 结果回填 → 循环直到 final
```

### 9.2 工具：档位决定装备

- 阅读者 / 验证者 / 写作者：终端白名单（§2.1 三层强制）
- 协调者：四原语（roster / assign / board / report）
- 全部工具用 JSON schema 声明；执行前过档位闸门——**同一个 agent，穿不同装备**

### 9.3 流式（流动思考的来源）

OpenAI 兼容 SSE，三类 delta，实时进 cell：
`content`（回答）/ `reasoning_content`（思考，GLM·DeepSeek 等通用）/ `tool_calls`（按 index 增量累积）

### 9.4 渲染：cell 就是它的 TUI（与插件成员的本质区别）

```
▸ thinking  先看 roster，确认 verifier 空闲…          (dim，流动)
▸ tool      roster()                                  → 3 人，verifier 空闲
▸ tool      assign(beta, 跑测试, dep=alpha)            → 已派工
▸ say       已拆解为 2 步并派工，等 alpha 完成后触发验收
────────────────────────────────────────────
 state: waiting(beta) · tokens: 12.4k · 任务: 拆解派工
```

- 事件追加进 cell 的 Tail——**复用流水滚动历史、独立滚动**
- 状态条拿到**真实** state（thinking / tool / waiting / done）与 token/成本——零抓屏
- 多个 Bot 并排、思考同屏可见：抓屏做不到，这正是驾驶舱的价值

### 9.5 运行形态

v0 进程内 async loop（实现 MemberDriver 契约，随时可拆成独立进程做崩溃隔离）。
工具面小 → 上下文天然小 → 暂不做完整压缩：工具输出截断 + 滚动窗口即可。

### 9.6 重试与失败处理（自然化：网络抖动是常态）

| 项 | 策略 |
|---|---|
| 总尝试次数 | **3 次**（首发 + 2 次重试） |
| 间隔 | **10 秒**（固定；可用 `KRYSTAL_RETRY_WAIT_MS` 覆盖，测试用） |
| 可重试 | 网络类（`fetch failed`/ECONNRESET/terminated）、超时、`HTTP 5xx`、`HTTP 429` |
| **不**重试 | 鉴权与参数类（400/401/403/404/422）——重试不会变好，立即停 |
| 用 esc 中断 | 重试等待可被立刻打断（可中断 sleep） |
| 三次仍失败 | **停下来**报错：`<原因>（已重试 2 次仍失败，停下）` |
| 可见性 | 界面显示 `⟳ <原因> —— 10 秒后重试（第 2/3 次）`，不让人干等（§10 可见性原则） |
| 流中断 | 重试前先关闭当前流式块（避免重复文本），已生成的片段保留可见 |

### 9.7 分期

| 版本 | 内容 |
|---|---|
| B0 | agent 核心：SSE 流式（三类 delta）+ 工具分发 + 档位闸门 |
| B1 | cell 渲染：思考/工具/回答行 + 底部真实状态行 |
| B2 | 协调者档位接四原语（roster/assign/board/report） |
| B3 | 写作者档位：工作副本 + 白名单 + 独立分支（§2.1 三层强制） |

## 10. 上下文管理（工作记忆：信噪比工程）

> 本节与 §11 的设计以**人脑为首要类比对象**：采用功能同构（工作记忆容量、固化、线索重建、
> 干扰抑制、遗忘即降权），**不宣称机制等同**。凡属隐喻处均标注「隐喻」。

### 10.1 问题的本质

模型训练分布是**人类书写的连贯文本**（信息密度高、冗余低）。上下文里混进了分布外的信息：

- 工具输出（一次列目录 200 行、报错堆栈 3000 字符——密度极低、占位极大）
- 重复状态（每轮重注的系统提示、文件清单、记忆段）
- 过程垃圾（试错命令、中间产物、被推翻的假设）

**所以上下文管理不是「记性问题」，是信噪比工程**：在固定窗口内维持有效信息密度，
使注意力不被稀释。agent 表现得"记性不好"，真相是重要信息被稀释到注意力阈值以下。

### 10.2 三堵墙，不是一堵

| 墙 | 性质 | 何时撞上 |
|---|---|---|
| 质量墙 | 长上下文检索精度随长度退化 | **最早**——远未满窗即开始 |
| 经济墙 | 每轮全量 prefill 的成本与延迟 | 缓存未对齐即撞 |
| 硬顶墙 | 物理截停、消息丢失 | 最后 |

结论：**不撑窗口，把状态搬出上下文**。上下文是工作台，记忆是仓库。（隐喻：工作记忆容量有限，
长时记忆近乎无限——瓶颈在检索与保持，不在存储。）

### 10.3 五层预算（装配优先级）

| 层 | 内容 | 保底策略 |
|---|---|---|
| 身份层 | 系统提示 + 档位策略 + 协作协议 | **永不裁剪** |
| 记忆层 | `MEMORY.md` / `AGENTS.md` 取 top（trust × 新近度）+ pinned | 预算内保底 |
| 工作集层 | 白板 + 当前任务 + 依赖/阻塞 | 保底 |
| 近期对话 | 最近 K 轮原文（含思考与工具调用） | **保底最近 K 轮** |
| 远期对话 | 摘要（原文在会话文件里，可检索） | **最先砍** |

超预算时的砍伐顺序：远期对话 → 记忆层低价值项 → 工作集次要项。**身份层永不动。**

### 10.4 回收顺序（先便宜后贵）

1. **工具输出折叠**：老的 `tool` 结果在上下文里换成一行 `…（已折叠 N 行，可 recall 取回）`
   ——**原文不删**，留在会话事件流里
2. **思考块折叠**：历史思考只留结论行（思考原文同样留档）
3. **远期轮次摘要**：把最老的一半做成一段 `[早期对话摘要]`——**搬迁，不是删除**

### 10.5 触发与可见性

- **真实 usage**：请求 `stream_options: { include_usage: true }`，从流末尾取真实 token 数
  （现在状态行显示的 `~0.6k tokens` 是字符估算，**必须换成真实值**）
- **窗口占用可见**：状态行显示 `上下文 62%`——人对自己的记忆负荷有感觉，agent 也该有
- **阈值**：70% 开始折叠工具输出；85% 触发摘要压缩；95% 强警告
- **窗口大小**：内置常见模型表 + 平台配置可覆盖（**不猜、不探测**）

### 10.6 明确不做（反模式）

- 无差别截断（等于丢信息，违反 §12 红线）
- 按轮数硬切（不看 token 实际占用）
- 把摘要当原文继续累积（摘要会再被摘要，误差复利）

## 11. 记忆与会话（记忆图）

### 11.1 一条流水线，不是两个系统

```
写入准入 ──→ 存储 ──→ 检索（路由）──→ 注入（装配）──→ 回收
 值不值得记   全量只增   该捞哪几条      预算内排列     搬迁/降权/归档
```

记忆与上下文是**同一条流水线的两个节点**：上下文管理的好坏直接决定记忆系统的表观脑容量。

### 11.2 三层存储（隐喻：人脑休息态压缩）

| 层 | 内容 | 媒介 | 访问路径 |
|---|---|---|---|
| 热层 | 当前工作集 | 上下文窗口 | 直接可见，用完即清 |
| 温层 | 全量原文（可检索） | `~/.krystal/sessions/*.jsonl` | `recall` 由线索捞回原文 |
| 冷层 | 蒸馏要点 + 记忆图 | `MEMORY.md` + `facts.jsonl` | 先粗筛，命中再回温层取原文 |

**两段检索**：冷/索引粗筛 → 温层原文精取。库容只增磁盘占用，**不增检索路径长度**。

### 11.3 记忆图（吸收 hermes holographic 的价值，去掉 HRR）

事实是节点，实体是边。每条事实一条 JSON：

| 字段 | 含义 |
|---|---|
| `id` | 稳定标识（时间戳 + 短随机） |
| `text` | 一句话事实（**一主题一条**，新信息更新旧条，不新开） |
| `entities[]` | 实体（文件 / 命令 / 成员 / 概念）——图的关键 |
| `by` | 断言者：`human` / `bot` / 成员名（团队场景） |
| `evidence` | 证据（`文件:行号`、命令输出片段、会话 id） |
| `trust` | 信任分（由反馈调整，非自动衰减） |
| `used` | 被召回次数（确定性信号） |
| `created` / `updated` | 时间**只作元数据**，不作结构 |
| `superseded_by` | 被哪条取代（**旧条不删**——搬迁原则） |

**实体抽取**：主路径 = 模型显式给（`remember(text, entities=[...])`，零 NLP、质量高）；
兜底 = 轻量正则（路径 / 扩展名 / 命令 / `@成员`），约 15 行。**不做**别名学习与实体消歧。

**不采用 HRR（全息约简表示）**：其价值在「无 schema 时也能做结构化检索」；我们**显式**存实体链接，
同样查询用 join 即可，且可读、可调试、**人可手改**。HRR 记为将来的优化位。

### 11.4 五个确定性查询（可离线评测）

| 查询 | 语义 | 回答的问题 |
|---|---|---|
| `recall(query)` | 关键词 + 图加权 | 「关于 X 我知道什么」 |
| `about(entity)` | 关于某实体的事实 | 「bot.ts 是什么」 |
| `related(entity)` | 共享实体的一跳邻居 | 「和它相关还有什么」 |
| `connect(a, b)` | 同时关联 a 与 b 的事实（交集） | 「A 和 B 之间是什么关系」 |
| `conflicts()` | 矛盾检测 | 「哪些断言互相打架」 |

全部**确定性、无向量库**（grep + 实体索引），因此评测不需基建（见 §12.2）。

### 11.5 注入装配（缓存友好是硬约束，见 §13）

**稳定序 + 只在记忆集变化时更新**（不做每轮重排——重排 = 前缀每轮变化 = 缓存全量失效）：

- 记忆块按**插入序**稳定排列，`pinned` 置顶；只有"记忆集合/ pinned 变化"时才重生成记忆块
- `superseded_by` 非空的条目**默认不注入**（但可 recall 找回）
- **年龄、召回次数、时间戳一律不进前缀**：它们是每轮都变的值 → 改为
  **按需由工具取**（模型问 `recall`/`about` 时随结果返回），或只进 UI。
  「时效可见」的需求靠 **pull**，不靠 push ✓
  （教训仍来自 bobo `TIME_DECAY`：轮次衰减分不清"活跃"与"新鲜"——但解法不是把年龄塞进 prompt）

### 11.6 反馈与信号（最小版）

- `remember(text, entities)` — 写入（准入 = 显式，不做"未来复用概率"预测器）
- `helpful(id)` / `wrong(id)` — 调整 trust（**显式、可审计**；比自动信号分更可靠）✓ 已实现（+0.2 / −0.3）
- `supersede(id, newText)` — 取代：旧条标 `superseded_by`，**不删** ✓ 已实现
- 以上都挂在**一个** `memory` 工具上（九个 op：remember/recall/about/related/connect/conflicts/helpful/wrong/supersede）
  —— 一个工具而非九个，省 token
- `used` 自增：召回命中即 +1（确定性，零 ML）

**不做**：自动信号分加减、时间衰减公式、contextual bandit、harness RL（"灵魂"）——留待有数据后再说。

### 11.7 与团队线统一（会话 = 事件流）

| 流水线节点 | 团队线现状 | 统一后 |
|---|---|---|
| 存储 | `board.md` + `team.json` + 快照 ✓ | 共用 `sessions/<id>/events.jsonl` |
| 注入 | `BRIEF.md` + 身份注入 ✓ | 共用登记器（五层预算） |
| 工作记忆 | 白板 ✓ | 白板 = 工作集的镜像 |
| **检索 / 回收** | ✗ 完全缺失 | `recall` / `connect` / `conflicts` |

**团队独门价值 ✓ 已实现（§14 决策后续）**：`krystal board` 的每条断言自动记入记忆图
（`scope = 团队 id`、`by = 团队/成员`、证据自动提取 `文件:行号`）；界面新增两个命令：
- `:memory` —— 团队记忆图（事实/实体/关联/矛盾统计 + 每实体事实树 + 关联边 + 文件路径）
- `:conflicts` —— 矛盾检测：成员断言互相打架时，**主动摆到人类面前**（人类只裁决冲突，不必逐格盯屏）

Bot 的全局记忆也不混进团队视图——**团队从此有记忆**（这是"多 agent"与"一堆 agent"的分水岭）。

## 12. 不变式、评测与红线

### 12.1 四个不变量（红线，任何改动不得违反）

1. **压缩 = 搬迁，永不删除**：原文必须留在温层（会话事件流），上下文里只放摘要与线索
   ——「不好的压缩比没有压缩更差」
2. **注入必须有预算**：任何"顺手把信息塞进上下文"的改动都要说明它占哪一层、挤掉谁
3. **记忆本地、不外传**：不联网、不上传（隐私铁律）
4. **算法改动必须有离线重放数据**：记忆/检索/注入的任何算法改动，无对比数据不予合并

### 12.2 评测指标（记忆的"体检"）

| 指标 | 定义 |
|---|---|
| **有效记忆周期** | 第 1 轮埋入事实，第 N+1 轮以线索式提问召回，测不同 N 的召回率**曲线** |
| 检索命中率 | 该捞的捞到没有 |
| 信噪比 | 注入段里有效信息占比 |
| token 效率 | 每轮 prompt token / 有效产出 |

配套脚本 ✓ 已实现：`scripts/recall-eval.ts <questions.json> [--limit N]`
输出：**命中率（recall@N）· 注入块 token 成本（信噪比）· 事实总数** + 逐条命中明细。
问题集格式：`[{ "q": "闸门白名单在哪实现", "expect": ["src/bot.ts","白名单"] }]`。

**中文检索**：中文没有词边界，整句会被当成一个 token → 检索用 **2-gram 展开**（不引入分词器）。
实测：同一问题集的命中率 25% → 50%（未命中的那条是该库确实没有的事实，属正确未命中）。

「有效记忆周期（recall@N 曲线）」需按轮次重放会话，属后续扩展（当前事实不随轮次衰减，
曲线是检索算法的函数而非时间的函数）。
**因为检索是确定性的（grep + 实体索引），评测零 API、零基建**——把红线 4 的成本降到几乎为零。
任何记忆类改动合并前，曲线不得变差。

### 12.3 神经科学对照表

| 人脑（隐喻） | Krystal 机制 |
|---|---|
| 工作记忆容量有限、注意瓶颈 | 五层预算 + 砍伐顺序（§10.3） |
| 长期记忆近乎无限、检索才是瓶颈 | 全量只增存储 + 五查询路由（§11.2–11.4） |
| 线索重建（不存原文，凭线索重建） | 上下文只放线索；`recall` 从原文取回 |
| 固化（consolidation） | 远期轮次 → 摘要搬迁（§10.4） |
| 干扰抑制（记得越多越互相打架） | 注入预算 + `conflicts()` 显式暴露矛盾（§11.5） |
| 遗忘 = 降权，不是删除 | `superseded_by` + trust 调整，原文永在 |
| 显著性/情绪加权 | `trust`（由显式反馈调整） |
| 睡眠期整理 | 冷层蒸馏（`MEMORY.md` 镜像 + 摘要库） |

## 13. 简洁性约束：不复杂化，以缓存命中率为判据

> 两条底线（owner 2026-09-23）：
> 1. **一切合理化、自然化，而不是复杂化**
> 2. 判断是否复杂化的关键指标：**缓存命中率**

### 13.1 为什么缓存命中率是判据

前缀缓存（prefix cache）的物理含义很直白：

| 命中 | 未命中 |
|---|---|
| 前缀逐字节相同 → 复用 KV，成本约 0.1x、延迟大幅下降 | 重新编码整段前缀 → 贵、慢 |

**未命中 = 「每轮被迫重新学习已经知道的东西」**——这正是不自然、不合理的地方。
所以：**任何降低命中率的设计，先按「过度复杂」处理**，除非有实测收益能证明值得。

### 13.2 可缓存的装配形状（硬约束）

```
[ 身份/系统提示 ]      ← 版本化：只在发版/档位变更时变
[ 记忆块 ]            ← 只在记忆集合变化时重生成（稳定序，不重排）
[ 工作集：白板/任务 ]  ← 低频变化
──────────────────── 以上为稳定前缀，其余全部追加
[ 对话历史 ]          ← 只追加，不重写（压缩除外，见 13.3）
```

**易变信息一律不进前缀**：时间戳、上下文百分比、token 计数、召回次数、条目年龄
→ 只进 UI，或**按需由工具取**（pull 而非 push）。

### 13.3 压缩与缓存的配合

- 压缩是**一次性重写事件**（阈值触发），不是持续行为；两次压缩之间前缀必须稳定
- **禁止「每轮摘要一遍」**：误差复利 + 每轮全量未命中
- 摘要插入位置固定（紧跟稳定前缀），减少尾部错位

### 13.4 反模式清单（"复杂化"的气味）

| 反模式 | 命中率后果 |
|---|---|
| 每轮重排记忆 / 工具清单 | 前缀每轮变 → 全量未命中 |
| 向前缀注入动态状态（时间、百分比、年龄、计数） | 同上 |
| 持续重写摘要 | 同上 + 误差复利 |
| 每轮重注身份/简报（团队线） | 同上（**已做对**：只在上下文新生时注入一次） |
| 无差别截断/重组历史 | 同上（违反 §12.1 红线①） |

### 13.5 度量与回归

- **两级度量**（实测教训：GLM 端点同前缀第二次调用仍报 `cached_tokens = 0`，故不能只靠 provider）：
  1. **本地「前缀稳定性」**（主判据，100% 可控）：每回合把装配好的稳定前缀做 SHA-1，
     与上一回合逐字节比对 → 状态行显示 `前缀 稳定` / `前缀 变化`。变红即说明我们自己在搅动上下文
  2. **远端 `cached_tokens`**（有则显示）：`prompt_tokens_details.cached_tokens`（OpenAI/DeepSeek 等）
     → 状态行 `缓存 78%`；provider 不报则显示 `缓存 —`
- **显示**：状态行 `上下文 62% · 缓存 78%`（只进 UI，不进 prompt）
- **回归**：任何上下文/记忆改动，**命中率不得下降**——与 §12.2 的 recall 曲线并列，
  作为第二条强制指标
- **期待基线**：稳定对话（无压缩）> 90%；压缩后一轮内回到 > 80%

### 13.6 与本设计的关系（自查结论）

现有实现已经是缓存友好的：系统提示稳定、历史只追加、身份只在上下文新生时注入一次。
风险全部来自**未来功能**（记忆重排、动态状态注入、持续摘要）——§13.4 就是给它们的禁令。

### 14.4 会话入口（对话内命令，不进向导）

**进入 Krystal Bot 永远是新的界面（新会话）**；历史靠对话内命令回溯（与 pi 同源）：

| 命令 | 行为 |
|---|---|
| `/resume`（等价 `:resume`、`/sessions`） | 列出历史会话（时间 · 模型 · 消息数 · 首句），↑↓ 选择 → enter 恢复（清空对话区并重放事件流） |
| `/new` | 开新会话（清空对话区，新 session id） |
| `/memory`（等价 `:memory`、`/mem`） | 打印**记忆图**：统计 → 每实体一棵事实树 → 实体关联（图的边）→ 矛盾 → 文件路径（可手改） |
| `/help` | 命令提示 |
| 其它 `/…` `:…` | **只提示，绝不发给模型**（平台约定：未知命令不广播） |

设计理由（对应底线一「不复杂化」）：向导少一层菜单；会话回溯是**低频动作**，
放在对话内按需触发，比每次进来都问「继续/新建」更自然。状态行常驻 `/resume 回溯` 提示。
